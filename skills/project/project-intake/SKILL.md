# Project Intake

Treat intake as a decision tool, not a questionnaire for its own sake.

## Routing profiles

### Product / app
Determine problem, users, buyer, value proposition, core workflows, MVP scope, platform, data, auth, integrations, monetization, success metrics, and constraints.

### Client
Determine client/business identity, authorized scope, existing assets, ownership, stakeholders, audience, required deliverables, approval process, deadline, budget constraints when known, brand rules, access boundaries, and handoff expectations.

### Website
Determine business objective, target visitors, conversion action, content hierarchy, pages, CMS/content needs, SEO needs, location/market, assets, brand, references, integrations, and responsive requirements.

### Business
Determine customer/problem, existing alternatives, acquisition path, geography, urgency, willingness to pay, trust barriers, economics, operational constraints, and validation plan before recommending software.

### Experiment
Determine hypothesis, success/failure criteria, scope, time box, environment, data needs, and what will happen to the result afterward.

## Question policy

Ask in rounds. Start with the smallest set that changes the solution. Do not ask for information the project template, repository, docs, or existing code already provides.

Use multiple-choice or short-answer options where that reduces effort.

If an answer is genuinely unknown, record it as `UNKNOWN` and move forward only where safe.

## Completion gate

Intake is complete when another competent agent could understand:

- why the project exists
- who it serves
- what must be built now
- what must not be built now
- where it will run
- what data/security constraints matter
- what success means

Produce a structured brief and list unresolved questions separately.
