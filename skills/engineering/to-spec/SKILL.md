# To Spec

Read the repository, domain context, ADRs, existing requirements, and relevant tests first. Synthesize known decisions rather than interviewing again.

Capture problem, outcome, scope, non-goals, externally observable behavior, domain rules, acceptance criteria, data/API implications, security implications, testing approach, and unresolved decisions.

Keep implementation details out unless they are part of an explicit external contract. The spec is a durable decision artifact, not permission to build or deploy.
